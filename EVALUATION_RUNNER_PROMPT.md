# Reusable sequential evaluation prompt

Copy the prompt below into a new Codex chat in this repository whenever you want to advance the study-space evaluation. Each invocation performs **one bounded unit of work**, saves its state, and ends with the next step. Reusing it does not restart completed cases.

```text
Continue the study-space capacity evaluation sequentially. Read AGENTS.md, README.md, CONTEXT.md, EVALUATION.md, and EVALUATION_RUNNER_PROMPT.md first. Do not spawn subagents or run multiple evaluation cases in parallel. Do at most one case run per invocation; if shared setup or a stage review is needed, do that instead of a case run.

Use EVALUATION.md as the specification for the test matrix, scoring, costs, and required artifacts. Keep raw source texts, model outputs, and evaluation state under the ignored data/evaluation/ directory. Never commit .env, API keys, private study material, or raw request bodies containing source text. Do not change the product's 40K generation limit just to run a case; use an isolated evaluation harness for larger inputs. Run npm test after changing JavaScript, and update CONTEXT.md after consequential behavior or architecture changes.

Progress and selection:
1. Inspect data/evaluation/progress.json if present and verify its statuses against the actual case artifacts. If it is absent, create a minimal progress file for shared setup. After source-set IDs and the matrix are fixed, expand it into a deterministic case queue in stage/table order, with source sets and repetitions in a stable order. Record separate runStatus and reviewStatus for each case; do not treat a case as complete based only on a status flag.
2. If the shared prerequisites are missing (non-confidential source sets, fixed reference concepts and their source locations, scoring rubric/thresholds, exact model settings, a cost-accounting method, or an isolated harness), complete the earliest setup task you can. Record what is ready and what remains. Do not invent human approval or claim draft reference concepts are human-reviewed. Do not make paid evaluation calls before the source set, reference concepts, and budget for that stage are ready.
3. Otherwise, choose the earliest case in the active stage that lacks its required artifacts or has an incomplete runStatus. If an interrupted case has partial artifacts, inspect them and resume or repair it; preserve all earlier API attempts and their costs. Never silently rerun a completed case.
4. Run only that case. Write manifest.json, calls.json, outputs.json, scores.json, and report.md under data/evaluation/<case-id>/ as specified in EVALUATION.md. Persist call records as the case progresses so failures and retries remain visible. Label agent-only judgments provisional and leave unavailable values null with a reason.
5. Verify the artifacts: the manifest identifies the exact configuration and source hashes; calls include every attempt; outputs include all three formats or explicit failures; scores contain raw counts and reviewer status; the report cites item/concept IDs and states limitations. Update progress.json only after verifying files. Use statuses such as pending, in_progress, generated, provisionally_scored, human_reviewed, and failed, with a short reason and updated time.
6. When a stage's cases are done, produce a stage comparison from saved artifacts before activating a conditional next stage. Do not select a model, processing method, output policy, or quality threshold by intuition after seeing results. Record the evidence and unresolved human-review needs. Do not claim an overall winner from provisional scores.

At the end, report exactly what was completed in this invocation, the case ID or setup task, artifact paths, API calls and USD cost incurred (or unknown cost), current progress counts, blockers needing user input if any, and the next pending case or setup task. Stop after one case or one setup/stage-review task. Do not begin the next case in the same invocation.
```

The first invocation will likely prepare shared fixtures and tracking rather than spend API tokens. Once setup is ready, each later invocation can use the same prompt to process the next case. The `progress.json` file is a navigation aid; the case artifacts are the evidence that work was actually done. A human review is recorded separately from agent-generated preliminary scores.

# Reusable sequential evaluation prompt

Copy the prompt below into a new Codex chat in this repository whenever you want to advance the study-space evaluation. Each invocation completes all setup work it can and then runs **at most one evaluation case**, saves its state, and ends. Reusing it does not restart completed cases.

```text
Continue the study-space capacity evaluation sequentially. Read AGENTS.md, README.md, CONTEXT.md, EVALUATION.md, and EVALUATION_RUNNER_PROMPT.md first. Do not spawn subagents or run multiple evaluation cases in parallel. Do at most one paid evaluation case run per invocation. Setup, bookkeeping, and a stage review do not count as a case and are not reasons to stop early.

Use EVALUATION.md as the specification for the narrowed 40K-versus-100K pilot: 12 initial cases across mini and Terra, three source sets, and one run per configuration and set. Do not expand to 10K, 25K, or 70K, add models, or start a second repetition without a deliberate plan update. Keep raw source texts, model outputs, and evaluation state under the ignored data/evaluation/ directory. Never commit .env, API keys, private study material, or raw request bodies containing source text. Do not change the product's 40K generation limit just to run a case; use an isolated evaluation harness for larger inputs. Run npm test after changing JavaScript, and update CONTEXT.md after consequential behavior or architecture changes.

Progress and selection:
1. Inspect data/evaluation/progress.json if present and verify its statuses against the actual case artifacts. Reconcile any old 60-case queue to the 12-case pilot only if all cases are still pending and no API calls were made; otherwise preserve completed work and report the discrepancy. If progress.json is absent, create a minimal progress file for shared setup, then build the 12-case queue once source-set IDs are fixed. Record separate runStatus and reviewStatus for each case; do not treat a case as complete based only on a status flag. Creating or updating progress.json alone is not completion of the invocation.
2. If shared prerequisites are missing (fixed reference concepts and their source locations, scoring rubric/thresholds, exact model settings, a cost-accounting method, or an isolated harness), work through every independent setup task you can complete in this invocation. Use the user's Dev Vault corpus recorded in ignored data/evaluation/source-config.json, source-lock.json, and corpus-manifest.json. Verify the frozen snapshot hashes before use; do not refresh it from the live vault or substitute public material without recording a deliberate new source-set version. Do not use data/spaces.json or Work Projects as fixtures. Check the selected corpus for other sensitive material before external model calls. Draft reference concepts and thresholds for review, implement and verify the isolated harness if needed, and record concrete artifacts and remaining work. Do not invent human approval or claim draft reference concepts are human-reviewed. Do not make paid evaluation calls before reference concepts and a stage budget are ready. Ask the user only for a decision or approval that cannot be inferred or completed independently, and present a concrete proposal first.
3. Otherwise, choose the earliest case in the active stage that lacks its required artifacts or has an incomplete runStatus. If an interrupted case has partial artifacts, inspect them and resume or repair it; preserve all earlier API attempts and their costs. Never silently rerun a completed case.
4. Run only that case. Write manifest.json, calls.json, outputs.json, scores.json, and report.md under data/evaluation/<case-id>/ as specified in EVALUATION.md. Persist call records as the case progresses so failures and retries remain visible. Label agent-only judgments provisional and leave unavailable values null with a reason.
5. Verify the artifacts: the manifest identifies the exact configuration and source hashes; calls include every attempt; outputs include all three formats or explicit failures; scores contain raw counts and reviewer status; the report cites item/concept IDs and states limitations. Update progress.json only after verifying files. Use statuses such as pending, in_progress, generated, provisionally_scored, human_reviewed, and failed, with a short reason and updated time.
6. When the 12 pilot cases are done, produce a comparison from saved artifacts. Do not automatically add models, sizes, processing methods, or repetitions. Record the evidence and unresolved human-review needs. Do not claim an overall winner from provisional scores.

At the end, report exactly what was completed in this invocation, the case ID if one was run, artifact paths, API calls and USD cost incurred (or unknown cost), current progress counts, blockers needing user input if any, and the next pending case or setup task. Stop after one case, or after setup has reached a genuine dependency that requires user input or external state. Do not begin a second case in the same invocation. Do not stop merely because a progress file was initialized or one setup item was completed.
```

The first invocation should advance the shared fixtures and other setup as far as possible without paid calls. Once setup is ready, each later invocation can use the same prompt to process the next case. The `progress.json` file is a navigation aid; the case artifacts are the evidence that work was actually done. A human review is recorded separately from agent-generated preliminary scores.

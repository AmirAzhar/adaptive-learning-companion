# Model-and-size pilot prompts (historical)

## Review the completed pilot with sub-agents

All twelve generation cases and provisional agent reviews are complete. These prompts document the pilot workflow; use the [concept-planning plan](../concept-planning/PLAN.md) for the next experiment. Agent scores must never be recorded as human review.

```text
Coordinate agent review of the completed 40K-versus-100K pilot. Read AGENTS.md, README.md, CONTEXT.md, evaluations/model-size/PLAN.md, and evaluations/model-size/RUNNER_PROMPT.md. The user authorizes sub-agents for review. Do not make OpenAI API generation calls, rerun cases, change product limits, or expose private corpus text in tracked files.

First inspect data/evaluation/experiments/model-size-pilot/progress.json, pilot-controls.draft.json and pilot-comparison.md in that same experiment folder, data/evaluation/reference-concepts.reviewed.json, and the twelve case directories under the experiment folder. Verify the generated artifacts and identify which reviews are missing. Prepare review packets under ignored data/evaluation/experiments/model-size-pilot/review/ with anonymous IDs. Each packet must contain the relevant frozen source documents, approved reference concepts, generated Main ideas/Quiz/Flashcards, and the scoring rubric, while omitting case ID, model, size label, manifest, call logs, cost, and latency. Keep the packet-to-case mapping in a separate coordinator-only file. Make packets independently readable; do not tell a reviewer to browse the case directory. A reviewer may infer size from source length, so describe the blinding as partial. Check that packet contents have no model or case labels before dispatch.

Spawn review sub-agents for independent packets. Give each agent only its assigned packet path and the rubric, and explicitly forbid reading the mapping, progress file, comparison, other packets, and case directories. Limit parallel work to available agent slots. Start with two independent agent reviews of the same packet from each of frontend, Java, and systems; use distinct output files per reviewer so they cannot overwrite one another. Compare their item-level and concept-level disagreements, resolve them against source passages, and record any rubric clarification before reviewing remaining packets. Then assign the other packets, again using separate output files and avoiding concurrent writes to shared state. Continue across chats from completed review files without repeating work.

For each packet and each of the three formats, score every applicable approved reference concept as 0, 0.5, or 1; score every generated item for correctness/source support and usefulness (0–2); flag serious errors, wrong quiz keys, duplicates, and missing high-priority concepts. Cite packet item IDs, reference concept IDs, and source locations for errors and borderline calls. Calculate raw numerators and denominators, high-priority coverage, and coverage by document and source third. Follow evaluations/model-size/PLAN.md and the approved thresholds; use null with a reason for anything not judged. Save each review and a short rationale under data/evaluation/experiments/model-size-pilot/review/ with reviewer type `agent` and status `provisional`. Never mark a case `human_reviewed`.

After reviews are saved, the coordinator verifies completeness and arithmetic, unblinds using the private mapping, and updates case scores or a separate aggregate without destroying the original pending scores or individual reviews. Update progress.json reviewStatus to `provisionally_scored` only for cases with complete verified agent scores. Produce a paired comparison by source set, model, size, and format, showing coverage, correctness, usefulness, balance, reliability, latency, cost, and threshold outcomes. Preserve the unknown cost of the timed-out call; do not count it as zero. State disagreements and the limits of agent-only review. Recommend whether 100K warrants a product change, a repeat, or another generation method, but label the recommendation provisional. Do not change the app limit in this invocation.

Report completed review IDs, unresolved disagreements, progress counts, and the next review task. If all reviews are complete, report the comparison and remaining decision instead. Make no paid API calls.
```

## Generate another case sequentially

Copy the prompt below into a new Codex chat in this repository whenever you want to advance the study-space evaluation. Each invocation completes all setup work it can and then runs **at most one evaluation case**, saves its state, and ends. Reusing it does not restart completed cases.

```text
Continue the study-space capacity evaluation sequentially. Read AGENTS.md, README.md, CONTEXT.md, evaluations/model-size/PLAN.md, and evaluations/model-size/RUNNER_PROMPT.md first. Do not spawn subagents or run multiple evaluation cases in parallel. Do at most one paid evaluation case run per invocation. Setup, bookkeeping, and a stage review do not count as a case and are not reasons to stop early.

Use evaluations/model-size/PLAN.md as the specification for the narrowed 40K-versus-100K pilot: 12 initial cases across mini and Terra, three source sets, and one run per configuration and set. Do not expand to 10K, 25K, or 70K, add models, or start a second repetition without a deliberate plan update. Keep raw source texts, model outputs, and evaluation state under the ignored data/evaluation/experiments/model-size-pilot/ directory. Never commit .env, API keys, private study material, or raw request bodies containing source text. Do not change the product's 40K generation limit just to run a case; use an isolated evaluation harness for larger inputs. Run npm test after changing JavaScript, and update CONTEXT.md after consequential behavior or architecture changes.

Progress and selection:
1. Inspect data/evaluation/experiments/model-size-pilot/progress.json if present and verify its statuses against the actual case artifacts. Reconcile any old 60-case queue to the 12-case pilot only if all cases are still pending and no API calls were made; otherwise preserve completed work and report the discrepancy. If progress.json is absent, create a minimal progress file for shared setup, then build the 12-case queue once source-set IDs are fixed. Record separate runStatus and reviewStatus for each case; do not treat a case as complete based only on a status flag. Creating or updating progress.json alone is not completion of the invocation.
2. If shared prerequisites are missing (fixed reference concepts and their source locations, scoring rubric/thresholds, exact model settings, a cost-accounting method, or an isolated harness), work through every independent setup task you can complete in this invocation. Use the user's Dev Vault corpus recorded in ignored data/evaluation/source-config.json, source-lock.json, and corpus-manifest.json. Verify the frozen snapshot hashes before use; do not refresh it from the live vault or substitute public material without recording a deliberate new source-set version. Do not use data/spaces.json or Work Projects as fixtures. Check the selected corpus for other sensitive material before external model calls. Draft reference concepts and thresholds for review, implement and verify the isolated harness if needed, and record concrete artifacts and remaining work. Do not invent human approval or claim draft reference concepts are human-reviewed. Do not make paid evaluation calls before reference concepts and a stage budget are ready. Ask the user only for a decision or approval that cannot be inferred or completed independently, and present a concrete proposal first.
3. Otherwise, choose the earliest case in the active stage that lacks its required artifacts or has an incomplete runStatus. If an interrupted case has partial artifacts, inspect them and resume or repair it; preserve all earlier API attempts and their costs. Never silently rerun a completed case.
4. Run only that case. Write manifest.json, calls.json, outputs.json, scores.json, and report.md under data/evaluation/experiments/model-size-pilot/<case-id>/ as specified in evaluations/model-size/PLAN.md. Persist call records as the case progresses so failures and retries remain visible. Label agent-only judgments provisional and leave unavailable values null with a reason.
5. Verify the artifacts: the manifest identifies the exact configuration and source hashes; calls include every attempt; outputs include all three formats or explicit failures; scores contain raw counts and reviewer status; the report cites item/concept IDs and states limitations. Update progress.json only after verifying files. Use statuses such as pending, in_progress, generated, provisionally_scored, human_reviewed, and failed, with a short reason and updated time.
6. When the 12 pilot cases are done, produce a comparison from saved artifacts. Do not automatically add models, sizes, processing methods, or repetitions. Record the evidence and unresolved human-review needs. Do not claim an overall winner from provisional scores.

At the end, report exactly what was completed in this invocation, the case ID if one was run, artifact paths, API calls and USD cost incurred (or unknown cost), current progress counts, blockers needing user input if any, and the next pending case or setup task. Stop after one case, or after setup has reached a genuine dependency that requires user input or external state. Do not begin a second case in the same invocation. Do not stop merely because a progress file was initialized or one setup item was completed.
```

The first invocation should advance the shared fixtures and other setup as far as possible without paid calls. Once setup is ready, each later invocation can use the same prompt to process the next case. The `progress.json` file is a navigation aid; the case artifacts are the evidence that work was actually done. A human review is recorded separately from agent-generated preliminary scores.
